# Contributing

How we work in this repository. Short version: `main` always holds working code, all work
happens on branches, and everything reaches `main` through a pull request reviewed by
@nicolaiberk.

If you are new to this workflow, the three sections below are meant to be followed in
order: **branch → commit → pull request**.

## Roles

- **Maintainer** (@nicolaiberk): owns `main`, reviews and merges all pull requests.
- **Contributors**: write access, work on branches, open pull requests.

Direct pushes to `main` are rejected by the server. This is not a convention you can work
around locally, so start every piece of work with a branch.

## 1. Start a branch

Whenever you want to add a feature, fix a bug, add data, or change anything else, open a
branch. Start it from an up-to-date `main`:

```bash
git switch main
git pull
git switch -c fix/s3-bucket-path
```

Name it `topic/short-description`, lowercase, hyphenated. The prefix says what kind of work
it is — that is why the commits themselves don't need type labels:

```
fix/s3-bucket-path              a bug in existing code
data/add-2024-wave              new or updated input data
scraper/nzz-encoding            work on a specific data source
analysis/party-fixed-effects    a new or revised analysis
refactor/split-prefect-flow     restructuring without changing results
```

Keep a branch to one task. If you notice an unrelated bug while working, note it and fix it
on a separate branch — do not smuggle it into the current one.

## 2. Commit as you go

Commit every small, self-contained change — not once at the end of the day. A good commit
is one thing you could describe in a single sentence without using the word "and".

```bash
git add scripts/upload.py
git commit -m "fix faulty path to S3 bucket"
```

**Write the message so that someone reading `git log` in a year knows what happened.**
Say what you did, in the imperative, specifically:

| Good | Bad |
| --- | --- |
| `fix faulty path to S3 bucket` | `update` |
| `add 2024 wave to comment database` | `data stuff` |
| `drop duplicated articles in NZZ scrape` | `fixes` |
| `switch topic model to 40 topics` | `changes to model` |

Keep the summary short (roughly one line). If the change needs justification — why 40
topics, why this filter — add a blank line and a short paragraph below it.

**Do commit as one unit:**

- One logical change, together with the comments or docs that go with it.
- A pure rename or reformat, on its own, with no substantive change mixed in.
- A dependency or environment change, on its own.

**Do not commit:**

- Half-finished code. Only commit code that runs — leave the experimental state in your
  working directory until it works, then commit it.
- Several unrelated changes at once because they happened in the same afternoon.
- Credentials, `.env` files, API keys.
- Generated output, cached files, notebook output, or anything above ~10 MB. If it can be
  regenerated by re-running the pipeline, it does not belong in git.

### Publishing the branch

Push the branch the first day you work on it, and keep pushing as you commit. It is a
backup, and it lets the maintainer see what is in progress.

```bash
git push -u origin fix/s3-bucket-path   # first time
git push                                # every time after
```

If `main` has moved on while you worked, bring your branch up to date before opening the
pull request, so the review shows only your changes:

```bash
git pull --rebase origin main
git push --force-with-lease
```

## 3. Open a pull request

When the overall task is finished — the feature works, the bug is fixed, the data is in —
open a pull request against `main`:

```bash
gh pr create --base main --fill
```

or on GitHub: the repository page will offer a **Compare & pull request** button for your
recently pushed branch.

@nicolaiberk is requested as reviewer automatically.

Fill in the description:

```markdown
## What
One or two sentences on the change.

## Why
The problem or decision this follows from. Can reference an issue.

## How to check
Which script to run, which file or figure to look at.

## Notes for the reviewer
Anything you are unsure about, or deliberately left out of scope.
```

Rules of thumb:

- One pull request = one reviewable idea. If the description needs bullet points for
  unrelated things, split it into two branches.
- Aim for a few hundred changed lines at most. Large pull requests get worse review, not
  better.
- Anything touching shared data, file paths, or the environment gets a pull request even if
  it is a one-line change.
- Respond to feedback with **new commits** on the same branch, then push — do not
  force-push during an active review, it destroys the reviewer's view of what changed.
- The **maintainer merges**, not the author. Merged branches are deleted.

### Before you mark it ready

- [ ] Branch is up to date with `main`
- [ ] The specific code runs end to end
- [ ] No credentials, large files, or notebook output in the diff
- [ ] Commit messages say what was actually done
- [ ] Description filled in
